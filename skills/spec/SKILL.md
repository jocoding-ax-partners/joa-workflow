# joa:spec

워크플로 1~3단계(기획·와이어프레임·Design 핸드오프)를 담당한다. 이 스킬 자체는 순서만
서술하고, 통과 판정은 전부 `${CLAUDE_PLUGIN_ROOT}/bin/joa.mjs` 가 한다.

## 1. 진입 가드

가장 먼저 실행한다:

```bash
node ${CLAUDE_PLUGIN_ROOT}/bin/joa.mjs require spec
```

exit 1 이면 **즉시 멈추고** 스크립트가 출력한 문장을 그대로 사용자에게 전달한다.

## 2. 1단계 기획 초안

`superpowers:brainstorming` 을 호출한다.

**⚠️ 종료 조건을 덮어쓴다.** brainstorming 의 기본 종료는 `writing-plans` 호출로 이어지지만,
이 워크플로에서는 **스펙 문서까지만 하고 멈춘다.** 계획은 4단계(`joa:front`)에서 mock 을 실측한
뒤 `joa:plan` 이 짠다. 여기서 곧장 계획으로 넘어가면 계약이 얼기 전에 병렬 기획이 시작되고,
그게 나중에 계획 사이 이음새가 비는 원인이 된다. brainstorming 이 "이제 계획을 짜자"고
제안해도 따르지 않는다.

다룰 것: 목적 · 필요한 것 · **오버엔지니어링 검문** · 개발 스펙 · 프레임워크 · 인프라 방향
(방향만, 상세 설계 아님).

## 3. 2단계 ASCII 와이어프레임

화면이 있는 기능일 때만 진행한다.

- **가로 180~200자.** 좁게 그리면 화면의 정보 배치가 실제 폭과 어긋난다.
- **한 문서에 전 화면을 담는다.** 화면별로 문서를 쪼개면 화면과 화면 사이의 흐름이
  문서와 문서 사이의 빈틈으로 사라진다.
- **와이어프레임마다 end-to-end 동작 설명 한 문단.** 그림만으로는 무엇이 클릭을 일으키고
  무엇이 응답인지 알 수 없다.

## 4. 3단계 Claude Design 핸드오프

여기서 말하는 디자인 도구는 외부 **Claude Design** 이다. **`frontend-design` 스킬을 쓰지
않는다** — 그건 이 단계의 대체물이 아니다.

와이어프레임 문서를 통째로 Claude Design 에 넣어 디자인을 뽑고 Export 하라고 사용자에게
지시한 뒤, **HTML 수령을 기다린다.** 기다리는 동안 다음 단계로 넘어가지 않는다.

## 5. 종료 게이트

사용자 승인과 산출물 존재가 게이트다. **기계로 잴 수 없는 판단이라는 것을 숨기지 않는다** —
`require`/`floor` 같은 자동 검사가 없다고 해서 게이트가 약한 것처럼 말하지 않는다.

승인된 내용이 나중에 산문으로 슬쩍 바뀌는 것을 막기 위해, 승인 시점 문서의 해시를 증거에
박는다:

```bash
shasum -a 256 docs/specs/<기능>.md docs/specs/<기능>-wireframe.md
node ${CLAUDE_PLUGIN_ROOT}/bin/joa.mjs pass spec "사용자 승인. 스펙 sha256=<앞 12자>, 와이어프레임 sha256=<앞 12자>, HTML 수령"
```
